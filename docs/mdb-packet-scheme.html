MDB Transaction Packets

One JSON packet per complete transaction instead of one text line per bus exchange. Flat short keys for the data, and a single field whose bits are the transaction's state — so a whole sale reads as "VEND": 63 and a stalled one reads as 3.

Design proposal · not implemented yet

01 · the problemWhy packets, when we already have a log

Today the device publishes one human-readable line per bus exchange (RX: 0x11, 0x01, ... -> TX: ACK). That is perfect for watching a machine live and useless for anything else: to answer "did machine 85E5F7 complete its handshake?" a backend has to re-implement the state machine by parsing English.

Log stream (today, unchanged)Packet stream (new)
Unitone line per exchangeone packet per transaction
Volumehundreds of messages/minutea handful/minute; zero while idle
Shapefree textJSON, flat short keys
Answers"what happened at 14:32:07?""which machines are stalling, and where?"
Audiencea person with the dashboard opena backend, a database, an alert rule

Nothing about the existing wire changes. Packets go to a new topic (.../packets); liveLog, commands, and every tagged message (VMC_STATUS:, SETTINGS_JSON:, CONFIG_JSON:) keep working byte-for-byte, so the current dashboard needs no changes at all.

02 · the containerThe packet shape

No envelope and no nesting. A packet is a flat object of short keys, and one of those keys names the packet type while also carrying its state — VEND, HSHAKE, or STAT. Which key is present is how a consumer knows what it received. 

{
  "VEND": 63,          // the transaction state, as bits - and the packet's identity
  "MSK":  63,          // which bits applied on this path
  "OUT":  "DISPENSED",
  "AMT":  3.75,
  "MIN":  375,
  "SLOT": 1,
  "TS":   1756312836682,
  "DUR":  8420
}

That is the entire packet — about 110 bytes for a full sale, and everything a backend needs to bank it, alert on it, or chart it. Raw wire bytes are deliberately not in here: the log stream already carries every byte, and duplicating them would make the packet ten times bigger to serve a different audience. Packets carry state and money; the log carries bytes.

03 · the decisionBits or array

Both forms you sketched work. They differ only in how the state field is encoded:

Bitwise integer

recommended
"VEND": 63,
"MSK":  63
  • Two integers cover the whole transaction state.
  • One arithmetic health check, no string work: (VEND & MSK) == MSK.
  • Indexable as a plain integer column; WHERE vend & 8 = 0 finds every non-dispensed sale.
  • Costs you readability — nobody eyeballs 51 and sees a decline.

Array of bits

alternative
"VEND": [1,1,1,1,1,1]
  • Readable at a glance in a raw log.
  • Can hold a third state directly (2 = not applicable) instead of needing a mask.
  • Roughly 6× the bytes, and still needs the position order documented — the readability is only as real as your memory of what position 4 means.

I would take the integer. The array's advantage is legibility, but the moment you need to know what position 4 is you are reading this page anyway — and the integer form is the one that makes fleet queries trivial instead of requiring JSON array indexing.

Bit order, stated once and explicitly

Bit 0 is the least significant bit and it is step 1. Step n has value 2n-1. This is worth being pedantic about: the one protocol bug in this project that survived review was exactly a bit-order mistake — the Level 3 optional-feature bytes are sent MSB-first, and reading them the intuitive way put "Always Idle" on the wrong byte. A bit ordering that is only implied is a bug waiting for a quiet afternoon.

Why a mask, and not just zeros. A zero bit is ambiguous on its own: at Level 1 the EXPANSION commands do not exist, and on a declined sale nothing is ever dispensed — those zeros are correct, not faults. MSK says which bits were expected on this particular path, so (VEND & MSK) == MSK means "everything that should have happened did", and MSK & ~VEND is exactly the set of steps that went missing. One expression, every level, every outcome.

04 · packetVEND — the money path

One packet per real transaction, spanning session open to session close — the six steps from your sketch, in order.

Data keys

KeyMeaning
AMTDisplay price, scale factor already applied — 3.75
MINExact integer minor units — 375. The figure to send a gateway; never do money maths on AMT.
SLOTItem/slot number the customer selected
OUTDISPENSED · DENIED · FAILED (approved, never dropped — refund) · CANCELLED · TIMEOUT
TS / DUREpoch ms at session open, and total duration in ms
MSOptional. Per-step offsets in ms, in bit order — [0,312,2104,6218,7902,8402]. This is where gateway latency lives (step 2 → step 3).
LVLMDB level in force, 1–3

OUT exists alongside the bits on purpose. The bits say what happened; OUT says what it means commercially, and the two are not derivable from each other — a declined card and a jammed motor both leave SUCC clear, but only one of them owes the customer money.

A completed sale

{
  "VEND": 63,          // 1+2+4+8+16+32 - every step
  "MSK":  63,
  "OUT":  "DISPENSED",
  "AMT":  3.75,
  "MIN":  375,
  "SLOT": 1,
  "LVL":  2,
  "TS":   1756312836682,
  "DUR":  8420,
  "MS":   [0,312,2104,6218,7902,8402]
}

Every other outcome, as numbers

VEND 63 / MSK 63 Sold. OUT:"DISPENSED". All six steps ran. (63 & 63) == 63 — clean.
VEND 51 / MSK 51 Declined. OUT:"DENIED". APRV and SUCC are clear and excluded from the mask — a decline is a normal outcome, not a fault, so this still checks clean. The session opened, the request came, and it closed properly.
VEND 55 / MSK 63 Jam. OUT:"FAILED". We approved, so success was expected — the mask keeps bit 4 in and the check fails: MSK & ~VEND == 8, precisely SUCC. This is the money-owed query: the customer paid and got nothing.
VEND 3 / MSK 63 App never answered. OUT:"TIMEOUT". Session began and the request arrived, then nothing. MSK & ~VEND == 60 — everything from approval onward is missing, which points at the payment app, not the bus.
VEND 62 / MSK 62 Level 3 Always Idle. No session begin exists on this path — the vend request arrives straight in ENABLED — so bit 0 is out of the mask and a perfect sale is 62, not 63.

05 · packetHSHAKE — coming up on the bus

One packet per setup handshake: from the machine's RESET to the device being live. Eight steps, so a whole handshake fits in one byte. This is the packet that says whether a freshly installed terminal actually joined the bus.

StepBitValueKeyMeansL1L2L3
101RSTRESET received, ACKed✓✓✓
212JRSTJUST RESET announced on a poll✓✓✓
324SCFGSetup config answered with reader config data✓✓✓
438SMAXSetup max/min prices ACKed✓✓✓
5416XREQExpansion request ID answered with peripheral ID—✓✓
6532XOPTExpansion enable options ACKed——✓
7664RENReader enable ACKed✓✓✓
87128LIVEFirst poll answered while enabled — bus proven alive✓✓✓

The level decides the mask, and nothing else: MSK 207 at Level 1 (no expansion commands exist), 223 at Level 2, 255 at Level 3. 

{
  "HSHAKE": 223,        // every step this level has
  "MSK":    223,        // Level 2: XOPT (32) is not expected
  "RES":    "OK",         // OK | STALL | RESET
  "LVL":    2,
  "RTY":    1,          // setup commands the machine resent and we re-answered
  "UNH":    0,          // commands addressed to us we could not answer
  "TS":     1756312834220,
  "DUR":    950,
  "MS":     [0,3,106,332,230,0,443,950]
}
HSHAKE 207 / MSK 207 Level 1, healthy. No expansion commands at L1, so 16 and 32 are out of the mask.
HSHAKE 223 / MSK 223 Level 2, healthy. Only enable options is out.
HSHAKE 255 / MSK 255 Level 3, healthy. Every step applies — a full byte.
HSHAKE 31 / MSK 223 Level 2, stalled. RES:"STALL". Setup finished, then reader enable never came: MSK & ~HSHAKE == 192 — REN and LIVE. The machine is not enabling the reader, which is a machine-side or config problem, and the number says so without anyone opening a log.

Note the MS array above is not ascending — step 5 sits at 230 ms while step 4 sits at 332 ms. That is a real trace from your machine: it sends setup max/min after expansion request ID, so a setup command lands when the device is already in DISABLED (which is what RTY:1 records). The bits stay in schema order and MS tells the truth about sequence, which is what lets one schema describe machines that disagree about their own handshake order. Steps that never happened carry 0.

06 · the volume ruleAuto-session: no customer, no packet

In auto-session mode the device opens a session the moment the reader is enabled, and re-arms after every close. A machine sitting idle overnight therefore opens and closes thousands of sessions in which nothing happens. Emitting packets for session begin, session complete and end session on their own would bury the real transactions and waste the broker.

So the VEND buffer is speculative:

  1. Session begin sets bit 0 in a buffer held in memory. Nothing is published.
  2. If a vend request arrives, the buffer is promoted to a real packet — bit 0 included, since it genuinely happened — and published when the session closes.
  3. If the session closes with no vend request, the buffer is discarded and only a counter increments.

Discarded is not invisible. Every suppressed session is counted in the STAT rollup as IDLE. Silently dropping them would make "quiet machine" and "dead machine" look identical — zero sales with 400 idle sessions is a healthy machine, while zero sales and zero idle sessions is one to go look at.

Manual mode follows the same rule: a session with no vend request produces no packet. The rule is about whether a customer transacted, not about which mode opened the session.

07 · packetSTAT — the rollup

One packet per window, and the only packet a healthy idle machine ever sends. Its value is the window length in ms, so the key still both names the packet and carries something useful. 

{
  "STAT": 60000,       // window length in ms
  "ST":   "ENABLED",    // MDB state at window close
  "SESS": 37,          // sessions opened
  "IDLE": 36,          // closed with no vend request - suppressed, per the auto-session rule
  "SALE": 1,           // VEND packets published - reconcile against what you received
  "POLL": 4318,        // polls answered - the bus-alive number
  "UNH":  0,           // commands addressed to us we could not answer
  "DROP": 0,           // packets lost to queue overflow since boot
  "TS":   1756312896000
}

SALE earns its place: with no sequence number anywhere in the scheme, it is the only way a backend can tell "this machine sold nothing" from "I lost the packet". Reconciling SALE against received VEND packets is the loss detector.

UNH is the one to watch. Every protocol bug found on real machines in this project started as an unhandled command — a rising UNH means the field is doing something the engine does not know about yet, and it is visible here without anyone reading a log.

08 · when packets open and closeLifecycle rules

A buffer must always close. These rules guarantee every opened buffer is either published or explicitly discarded — a half-finished transaction is data, not something to throw away.

HSHAKEVEND
Opens onRESET received, or the first setup command after the port openssession begin — or the vend request itself when Always Idle skips it
Publishes whenLIVE is set (first poll answered while enabled)the session closes — and only if a vend request was seen
Discards whenneverthe session closes with no vend request → STAT.IDLE++
On timeoutno progress for 30 s → publish with RES:"STALL"no progress for 120 s → publish with OUT:"TIMEOUT"
On RESET mid-flightpublish the partial with RES:"RESET", then open a fresh onepublish the partial with OUT:"CANCELLED" if a vend request was seen, else discard
On port closeflush the partial, same rulesflush the partial, same rules

A stalled vend is the most valuable packet in the system and the easiest to lose. If a machine dies mid-transaction and the buffer just sits there, that transaction is never reported — which is exactly the case someone will be asking about. Hence the timeout flush, and hence the ring buffer: a packet that could not be published while the broker was unreachable is still recoverable.

The two buffers are independent and at most one of each exists at a time. A VEND buffer open when a RESET arrives is resolved by the rule above before the new HSHAKE buffer opens, so they can never interleave in a way that loses a transaction.

09 · where it plugs inTransport & control

Topic

cm30-mdb/hamdan-rabbah/<deviceId>/packets     // new - one JSON packet per message
cm30-mdb/hamdan-rabbah/<deviceId>/liveLog     // unchanged
cm30-mdb/hamdan-rabbah/<deviceId>/commands    // unchanged

A separate topic, not a tagged line on liveLog, for one decisive reason: a backend that wants transactions should be able to subscribe to .../+/packets and get a few messages a minute instead of filtering a firehose. It also means the dashboard sees nothing new and cannot break. No new MQTT plumbing is needed either — MqttLib.enqueue() already takes a custom topic suffix. The device id is not inside the packet because the topic carries it; store packets with their topic, not detached from it.

Queue policy

  • Packets ignore setMqttLogging(off). That switch exists to silence chatter; packets are the opposite of chatter. Muting the log must never stop transaction reporting — they get their own switch.
  • Packets are protected from log-burst eviction. The outbound queue drops oldest on overflow, and a burst of log lines must not be able to evict a transaction record. Simplest viable approach: a small dedicated queue for packets, drained by the same publisher thread. Worth confirming against the current single-queue implementation before building.

Proposed control surface

Each one available both as an Android function and as a dashboard command, as with everything else in this library:

AndroidDashboard commandEffect
setPacketStream(Boolean)setPacketStream:on|offMaster switch. Default on.
setPacketTiming(Boolean)setPacketTiming:on|offInclude the MS array. Off shaves the packet to ~110 bytes; on is worth it while commissioning machines.
setStatWindow(seconds)setStatWindow:60STAT rollup period. 0 disables STAT.
lastPackets(n)getPackets:5Replay the last n from the ring buffer.
packetListener—Local callback with the same JSON, so an app can store or forward packets with no MQTT at all.

packetListener matters more than it looks: it means the packet scheme is not an MQTT feature. A device with no broker still produces the same records, and the app can ship them over its own channel.

10 · the payoffWhat a consumer actually does with this

Every one of these is arithmetic on two integers — no log parsing, no JSON walking:

QuestionExpression
Did everything that should happen, happen?(VEND & MSK) == MSK
What exactly went missing?MSK & ~VEND → look up the bit values
Money owed back to customersOUT = 'FAILED', or (VEND & 4) && !(VEND & 8) — approved but never dispensed
Is this machine even on the bus?a HSHAKE where (HSHAKE & MSK) == MSK
Where do failing terminals get stuck?group by MSK & ~HSHAKE
Which terminals have slow gateways?MS[2] - MS[1] — vend request to approval
Decline rate per machineOUT = 'DENIED' ÷ all VEND packets
Are we losing packets?STAT.SALE vs VEND packets received
Is a quiet machine dead or just idle?STAT.POLL high with STAT.SALE zero = idle and healthy
Is the field doing something we don't handle?STAT.UNH rising

Decisions to confirm before this gets built

  1. Integer or array for the state field — my recommendation is the integer plus MSK, but the array is a one-line change to the builder if you would rather read the packets by eye.
  2. Six VEND steps as listed, matching your sketch. The alternative is splitting step 3 into "app answered" and "answer sent on the wire", which would separate a slow gateway from a slow bus — currently both look the same in the bits, and only MS tells them apart.
  3. APRV means specifically "approved", so a decline leaves it clear and masks it out. If you would rather the bit meant "we answered, either way", say so — that shifts what a decline looks like from 51 to 55.
  4. Does the dashboard get a packet view, or is this backend-only for now? Either way the dashboard needs no change.
