Every command, and how it works

The complete developer manual for hardware-lib and mqtt-lib: every function with a working example, every dashboard command, and what actually happens inside when you call each one. Current as of hardware-lib 7.17.0 / mqtt-lib 2.4.0.

NEW — the 7.x splithardware-lib: the MDB engine, MQTT-free

mdb-lib is now hardware-lib-7.17.0 — renamed, and with the entire MQTT layer removed from inside it. The engine is pure hardware/protocol: everything it produces exits through listeners, everything it accepts enters through plain functions. The Kotlin package stays com.rabbah.mdb and a deprecated typealias MdbLib = HardwareLib keeps existing code compiling.

The MQTT wiring that used to be automatic now lives in a ~30-line app-side bridge (MdbMqttBridge.kt, shipped in samples/) that reproduces the old wire format byte-identically — the dashboard needs zero changes:

// the whole bridge - attach BEFORE HardwareLib.init():
MqttLib.addCommandListener { HardwareLib.handleCommand(it) }        // commands in
HardwareLib.addControlListener { tag, payload ->                     // control plane out
    if (tag == "LOG") MqttLib.enqueue(payload) else MqttLib.enqueue("$tag:$payload")
}
HardwareLib.addExchangeListener { e ->                             // exchanges out
    if (e.publishRemote) {
        RabbahLog.sessionId = e.sessionId
        RabbahLog.log(MdbLogEvent.valueOf(e.logEventName), e.params)
    }
}

New listener surface: stateListener (plain state name, edge-triggered on every transition), exchangeListener (one structured MdbExchangeEvent per exchange), controlListener (tag + JSON for SETTINGS_JSON / CONFIG_JSON / VMC_STATUS / LOG), plus the existing vendListener / logListener / statusListener. New input: HardwareLib.handleCommand(text): Boolean — feed it whatever any transport receives; it consumes what it recognizes.

Remote everything in one call (7.16.0): HardwareLib.attachLogSink { line -> send(line) } pipes every library line AND every control snapshot (CONFIG_JSON:, RS232_RULES_JSON:, ...) into whatever transport the host app already has — pair it with feeding the app's command channel into handleCommand and a dashboard sees and controls the whole library. Apps on our mqtt-lib need exactly one call instead: HardwareLib.attachRabbahMqtt() (reflection — no compile dependency). Send help as a remote command to get the full command list back as a log line.

Zero-wiring rescue (mqtt-lib 2.3.0): the app doesn't even need that one call any more. On the first successful broker connection mqtt-lib itself reflectively runs HardwareLib.attachRabbahMqtt() (MqttConfig.autoAttachHardware, default true) — swapping in the two current AARs is the entire integration. Two new commands are answered by mqtt-lib directly, so they work even on a device whose app never wired hardware-lib: attachHardware (wire the bridge on demand; reports success or why not) and version (reports the mqtt-lib and hardware-lib versions actually running). Field rule of thumb: ping answers PONG but every other command comes back [remote] unknown command → mqtt-lib is alive, hardware-lib is not attached — send version, then attachHardware.

New in 7.1.0 / mqtt-lib 2.0.0: (1) MQTT connection status, event-driven — RabbahMqtt.onConnection { connected -> ... } (or MqttLib.addConnectionListener) fires once immediately with the current state and then exactly once per change; RabbahMqtt.isConnected reads it on demand. The demo app logs [mqtt] CONNECTED to ... / [mqtt] DISCONNECTED - reconnecting.... (2) VMC_STATUS is now fully event-driven — it publishes on state transitions, on recentActivity flips and on start/stop; the periodic 3-second heartbeat is gone. (3) Every call answers true/false — no public function returns nothing: lifecycle, session/vend, every setting and every mqtt-lib call returns Boolean (true = done/queued, false = rejected or not applicable). Only setConfigHex / setReplyHex differ: null on success, else the error sentence.

logListener vs exchangeListener — same event, two formats

When the machine sends a frame and the library replies, BOTH listeners fire with the same exchange — the difference is only the shape you receive it in:

VMC sends 11 00 ... -> library replies READER CONFIG DATA
        |
        +- logListener gets ONE STRING (ready to show):
        |     "SETUP CONFIG rx=SETUP CONFIG tx=READER CONFIG DATA level=2" (rx = command NAME since 7.6.1)
        |
        +- exchangeListener gets AN OBJECT (ready to use):
              code = 113, rxHex = "11 00 03 10", txName = "READER CONFIG DATA", sessionId, ...

logListener = text, for display — a TextView, Logcat, a log file; you cannot easily ask "was this code 113?" without parsing the sentence. exchangeListener = data, for logic — if (e.code == 113) ..., analytics, forwarding, saving hex; its e.message is the identical sentence logListener receives. One extra scope difference: logListener ALSO hears the engine's status lines ([remote] vend approved requested, open() failed..., config acks), while exchangeListener fires strictly for bus exchanges.

Rule of thumb: show text to a person → logListener; make a decision in code → exchangeListener; both jobs in one app → attach both (different slots, no conflict).

Multiple consumers — add/remove listeners (7.2.0)

Each HardwareLib.xListener = { ... } var is a SINGLE slot: a second assignment silently replaces the first — which used to bite when your own code and MdbMqttBridge both wanted the exchange feed. Since 7.2.0 the bridge registers through the multi-listener API, so the var slots are always free for your code, and any number of extra consumers can register:

val mine: (MdbExchangeEvent) -> Unit = { e -> if (e.code == 11) charge(e.params[2].toInt()) }
HardwareLib.addExchangeListener(mine)      // alongside the bridge, alongside the var slot
HardwareLib.removeExchangeListener(mine)   // true when it was registered

// same pattern for the other feeds:
HardwareLib.addLogListener / removeLogListener
HardwareLib.addStateListener / removeStateListener
HardwareLib.addControlListener / removeControlListener

If exchangeListener seems to receive nothing, check in this order: (1) hardware-lib < 7.2.0 and the bridge overwrote your assignment — upgrade, or use addExchangeListener; (2) no real VMC is connected — exchange events fire only for actual bus frames (a dead port shows as open() failed... through logListener); (3) the listener was attached after the exchanges happened — there is no replay, only live events from the moment of registration.

The built-in self-test (7.3.0): HardwareLib.simulateExchange("10 10") pushes a fake RESET through the exact classify → template → listener pipeline — no machine, no open port needed (listeners fire synchronously on the calling thread). The demo app runs it once at boot, so the screen always shows [exchange] code=111 RESET_ACK rx=10 10 tx=ACK within a second of launch. The boot banner also prints HardwareLib.VERSION, catching a stale bundled AAR in one glance. Dashboard equivalent: the command simulateExchange:10 10 (any hex works).

Empty-session suppression (7.7.0): in AUTO session mode the machine cycles BEGIN SESSION → SESSION COMPLETE → END SESSION endlessly with no customer. Those cycles now log NOTHING by default - the BEGIN event is held back and delivered only when a VEND REQUEST arrives in that session, so a real transaction still logs its complete chain in order. Toggle with setEmptySessionVisibility:on|off (or HardwareLib.setEmptySessionVisibility(true)) to see every cycle again.

One code space end to end — MDB 110–136, RS232 137–143. 01Getting started

Add the AARs (or the Gradle modules) and initialize once at app startup:

// build.gradle (raw AARs; skip if using the Gradle modules directly)
implementation files('libs/mqtt-lib-2.4.0.aar')
implementation files('libs/hardware-lib-7.17.0.aar')
implementation files('libs/CM30-HardwareLibrary-1.0.9.aar')  // hardware-lib's hardware runtime
// In your Application class or first Activity - the whole startup:
val deviceId = Settings.Secure.getString(contentResolver, Settings.Secure.ANDROID_ID)
    .takeLast(6).uppercase()          // stable per device, no permission needed

MqttLib.init(MqttConfig(topicPrefix = "devices", deviceId = deviceId,
    logTopicSuffix = "logs", commandTopicSuffix = "cmd", statusTopicSuffix = "status"))
    // backend contract: devices/<id>/logs out, devices/<id>/passthrough in (auto-subscribed
    // since 2.1.0 - where the dashboard sends ALL commands), retained presence on .../status
MqttLib.start()                          // connect + reconnect loop + publisher thread
// MdbMqttBridge.attach() - OPTIONAL since mqtt-lib 2.3.0: the first successful connection
// auto-attaches hardware-lib (logs + remote commands) by itself. Keep the explicit bridge
// only if you need custom listener wiring; calling both is safe (attach is idempotent).
HardwareLib.init(applicationContext)          // persistence + settings restore (no networking inside)
HardwareLib.start()                           // open the MDB port + worker loop
// From here: all MDB data streams to the dashboard, all remote commands work.
  • Order matters, gently: call MqttLib.init() and attach the bridge before HardwareLib.init() if you want the dashboard link — init() publishes the first settings snapshot through the bridge. (Skipping MQTT completely is also fine — see the next section.)
  • applicationContext is the app-lifetime Android Context — the library needs it only for SharedPreferences. Passing an Activity works too (the library unwraps it), but the application context is the clean form.
  • Topics follow the backend contract: devices/<id>/logs out, devices/<id>/passthrough in (operator/dashboard commands — the backend owns devices/<id>/cmd with its ack/progress flow), retained presence on devices/<id>/status. The desktop dashboard watches both this scheme and the legacy cm30-mdb/hamdan-rabbah/<id>/liveLog world at once.

02What if I never initialize MQTT — does everything break?

No. MDB runs fully offline. This was a real bug found while writing this manual — before mqtt-lib 1.1.0, skipping MqttLib.init() made HardwareLib.init() crash on an uninitialized topic. Fixed: every MQTT call is now safe in every order.

You skipped MQTT and…What happens now
HardwareLib.init() / start()Works fully. Bus handshake, vend flow, VendListener, logListener, statusListener, settings, hex configs — all normal.
The engine tries to publish logs / status / acksEach enqueue() is a silent no-op. Nothing thrown, nothing lost locally — only the remote log is absent.
Dashboard remote commandsDon't arrive (there's no connection) — use the equivalent Android functions instead; every command has one.
MqttLib.enqueue("...") from your own codeSilent no-op.
MqttLib.start() without init()The one deliberate error: throws IllegalStateException("MqttLib.init(config) must be called before start()") — a clear message at the exact mistake, not a mystery crash later.
You call MqttLib.init()+start() LATERThe link simply comes up then. Messages enqueued before init are gone (they were no-ops); everything from that moment flows normally.

Rule of thumb: MQTT is the optional half. hardware-lib never requires it to vend — it only uses it when it's there. The only hard requirement is HardwareLib.init(context) before HardwareLib.start() (the engine needs its persisted settings and payloads loaded before touching the bus).

03Lifecycle functions

MqttLib.init(config: MqttConfig)

Stores the config and derives the topics: the log stream out (<prefix>/<deviceId>/<logTopicSuffix>), TWO command channels in (…/<commandTopicSuffix> and, since 2.1.0, …/<passthroughTopicSuffix>, default passthrough — same listener chain, kept separate so operator commands never mix into a backend-owned cmd topic), and optional retained presence. No network yet.

MqttLib.start() / MqttLib.stop()

start() launches two threads: the connect/reconnect loop (retries every 3 s forever) and the single publisher thread that drains the queue. It never blocks your caller and never fails because the broker is down — it just keeps retrying. stop() closes the socket and parks both threads.

HardwareLib.init(context: Context)

Loads persisted settings and hex payloads from SharedPreferences, and registers the MDB command listener on MqttLib (if MQTT is initialized, now or never — both fine). Idempotent: calling twice does nothing the second time.

HardwareLib.start() / HardwareLib.stop()

start() opens the CM30 MDB port and starts the worker loop that answers the VMC. All engine state resets to INACTIVE and the status is announced immediately. stop() closes the port, resets to INACTIVE, and announces that too — the dashboard's status bar flips instantly, not on the next heartbeat.

// Dashboard equivalents:  open  /  close
HardwareLib.start()
HardwareLib.stop()

04Vend actions & the payment flow

HardwareLib.vendListener — the payment hook

Four typed callbacks; override only what you need. All fire on a dedicated callback thread (never the bus thread itself — the bus loop only queues the event and goes straight back to answering the VMC, so even a slow callback can't make a response miss the machine's few-millisecond reply window). Still return promptly and do gateway work on your own coroutine/thread: the same queue also delivers log lines and status updates. Exceptions you throw are caught and logged, never fatal. The engine keeps ACKing the VMC's polls while your gateway call is in flight (the spec's delayed-response pattern), so a few seconds of latency costs nothing on the bus.

// The complete payment integration:
HardwareLib.setCancelMode(HardwareLib.CancelResponse.VEND_DENIED)   // once ever - persisted

HardwareLib.vendListener = object : HardwareLib.VendListener {

    override fun onVendRequest(amount: Double, minorUnits: Int, itemNumber: Int) {
        // amount = 3.5 (decimal, for display); minorUnits = 350 (EXACT integer
        // halalas - use this for the gateway and all money math). The library
        // already applied the scale factor. itemNumber = raw code, -1 if omitted.
        scope.launch {
            val ok = paymentGateway.authorize(minorUnits)  // HOLD the money, don't take it
            if (ok) HardwareLib.approveVend()                   // VEND APPROVED on next POLL
            else    HardwareLib.cancelVend()                    // standing cancel response
        }
    }

    override fun onVendSuccess(itemNumber: Int) {
        // MACHINE-side fact: the product physically dropped. NOW take the money.
        scope.launch { paymentGateway.capture() }
    }

    override fun onVendFailure() {
        // MACHINE-side fact: jam/empty - customer got nothing. Give the money back.
        scope.launch { paymentGateway.refundOrVoid() }
    }

    override fun onSessionEnded() {
        // Fires after EVERY session (sale, decline, jam, cancel, walk-away).
        // Cleanup only - never money decisions (you can't tell WHY it ended here).
        clearTransactionState(); resetUiToIdle()
    }
}

Why authorize/capture split: your approval is only permission — the machine then physically tries to dispense, and only IT knows if the customer is holding the product. onVendSuccess/onVendFailure are the machine reporting that physical outcome. Capturing on success (not on approval) means a jammed machine never takes anyone's money.

The price arrives ready to charge — in two forms, no math needed

On the MDB wire, prices are raw scaled units (a SAR 3.50 item travels as 350). The library converts BEFORE calling you, using bytes 4 and 5 of the live READER_CONFIG_DATA — the same values the VMC itself was configured with, so the two sides can never disagree:

  • minorUnits: Int = 350 — exact integer halalas/cents, computed with pure integer arithmetic. Use this for the gateway and any money math; most gateways take minor units natively, and integers can never carry floating-point error.
  • amount: Double = 3.5 — the decimal form, for display. Note Double is floating point: 3.50 prints as "3.5" unless you format it (String.format("%.2f", amount) → "3.50"), and some values (3.30) aren't exactly representable — fine for showing on screen, wrong for accumulating totals. That's exactly why minorUnits exists.

Standalone converters are also public: HardwareLib.priceToAmount(raw) and HardwareLib.priceToMinorUnits(raw).

HardwareLib.beginSession()

Arms BEGIN SESSION for the next POLL — the "card tap". In auto-session mode (default) this is never needed; in manual mode it's the only thing that starts a session. Call it from your NFC/tap detection. Dashboard: beginSession.

HardwareLib.approveVend(): Boolean

Arms VEND APPROVED. Returns false (and does nothing) if no VEND REQUEST is actually pending — an early or stale approval can never charge the next customer's selection. One call per vend; the response goes out on the next POLL. Dashboard: vendApprove.

HardwareLib.cancelVend(): Boolean

The simple cancel: aborts the live session on the next POLL, sending the standing response configured once via setCancelMode(). Works before OR after a VEND REQUEST (you can abort a session before the customer picks anything). No-op returning false if no session is live. One call per cancel. Dashboard: cancelVend.

HardwareLib.cancelVend(response: CancelResponse): Boolean

Same, but sends exactly SESSION_CANCEL_REQUEST or VEND_DENIED this one time, without touching the standing mode. Dashboard: cancelVend:sessionCancel / cancelVend:vendDenied.

HardwareLib.setCancelMode(mode: CancelResponse)

Set ONCE (persisted): what plain cancelVend() sends, and how the VMC's own VEND CANCEL (13 01) is answered. Different VMCs expect different responses — that's why it's configurable. Dashboard: setCancelMode:sessionCancel / setCancelMode:vendDenied.

05Seeing the MDB state from Android

HardwareLib.currentState      // "INACTIVE_STATE" | "DISABLED_STATE" | "ENABLED_STATE" | "VEND_STATE"
HardwareLib.isSessionActive   // true between BEGIN SESSION and END SESSION - the only window
                         // where approveVend()/cancelVend() can do anything

HardwareLib.statusListener = { json ->
    // {"state":"VEND_STATE","recentActivity":true}
    // fires INSTANTLY on every state transition + whenever bus activity appears or disappears (event-driven, the periodic heartbeat is gone)
    runOnUiThread { stateBadge.text = JSONObject(json).getString("state") }
}

HardwareLib.logListener = { line, showOnScreen ->
    // every log line the engine reports. showOnScreen == false marks per-poll
    // noise (idle POLL/ACK, unhandled) - do NOT render those into a growing
    // text view, that freezes a UI on real hardware. Never re-enqueue these.
    if (showOnScreen) runOnUiThread { appendToMyLogView(line) }
}

The four states: INACTIVE (port closed / pre-setup handshake), DISABLED (configured, waiting for READER ENABLE), ENABLED (open for business, waiting for a session), VEND (session live: requests, approvals, dispensing).

06Settings

All persisted in SharedPreferences (survive restarts), all mirrored to the dashboard via SETTINGS_JSON: on every change, all settable from either side.

HardwareLib.setAutoSession(enabled: Boolean) · HardwareLib.isAutoSession

true (default): sessions begin by themselves on READER ENABLE and after every END SESSION. false: only beginSession() starts one. Switching mid-session cancels the live session so the new mode applies immediately; switching while merely enabled arms/disarms on the spot. Dashboard: setSessionMode:auto|manual.

HardwareLib.setMdbLevel(level: Int) — 1, 2, or 3

Changes which setup handshake runs, the feature level reported in READER CONFIG DATA, and which BEGIN SESSION / PERIPHERAL ID payloads are sent. Level 1: shortest, no EXPANSION commands. Level 2: adds EXPANSION REQUEST ID / Peripheral ID. Level 3: adds EXPANSION ENABLE OPTIONS + the 4 optional-feature-bits bytes. Throws on any other value. Dashboard: setMdbLevel:1|2|3.

HardwareLib.setPollVisibility(show) · setUnhandledVisibility(show)

Log-debug toggles: report idle POLL→ACK exchanges / report commands unrecognized in the current state. Off by default (noisy). They never touch the on-device screen path — only what gets reported remotely. Dashboard: setPollVisibility:on|off, setUnhandledVisibility:on|off.

HardwareLib.setMqttLogging(enabled: Boolean) · isMqttLoggingEnabled

Master on/off for publishing the engine's log lines over MQTT. Persisted. While OFF: the local logListener still gets every line (your on-device log keeps working), and the control plane keeps publishing — VMC_STATUS status events, SETTINGS_JSON, CONFIG_JSON, PONG — so the dashboard still sees the device state and can still send commands, including setMqttLogging:on to turn the stream back on. Only the log traffic goes quiet (useful to cut broker traffic in production, or when many devices share one topic prefix). Dashboard: setMqttLogging:on|off.

HardwareLib.setMqttLogging(false)   // production: quiet the remote log stream
HardwareLib.setMqttLogging(true)    // debugging session: stream everything again
HardwareLib.isMqttLoggingEnabled    // current state

HardwareLib.currentSettingsJson(): String

Everything above as one JSON string — the same content the SETTINGS_JSON: message carries (includes mqttLogsEnabled). Dashboard: getSettings.

07Hex payload configuration

Every byte the device sends on the bus is editable — from Android code or from the dashboard, hitting the same store. Byte LENGTH is locked per payload (only values change), with one exception: the two BEGIN SESSION payloads accept ANY length from 1 to 35 bytes, because real machines disagree — some feature-level-2 VMCs only accept the short Level-1-style 3-byte form, so you store exactly the bytes your machine wants. Accepted values persist and are used on the very next send, no restart. Every change publishes an ack line ([app] or [remote] tag shows who did it) plus a fresh CONFIG_JSON: snapshot, so the dashboard's Config panel always shows confirmed device state.

// read / write / reset - names via constants, never raw strings:
HardwareLib.getConfigHex(HardwareLib.ConfigName.SESSION_BEGIN)                // "03 FF FF"
HardwareLib.setConfigHex(HardwareLib.ConfigName.SESSION_BEGIN, "03 07 D0")    // null = ok, else error text
HardwareLib.resetConfig(HardwareLib.ConfigName.SESSION_BEGIN)                 // back to library default
HardwareLib.configNames()                                                // all editable names
HardwareLib.configSnapshotJson()                                         // everything as JSON

// BEGIN SESSION length is editable (1-35 bytes) - e.g. a feature-level-2 machine
// that only accepts the short Level-1-style form:
HardwareLib.setConfigHex(HardwareLib.ConfigName.SESSION_BEGIN_L2, "03 FF FF")   // 3 bytes: accepted

// every other payload stays length-locked - validation is per call, handle the error:
val err = HardwareLib.setConfigHex(HardwareLib.ConfigName.VEND_APPROVED, "05 07")
// err == "Wrong length for VEND_APPROVED: got 2 byte(s), need 3"

// enable Level 3 "Always Idle" = bit 5 of the LAST feature byte (Z34):
HardwareLib.setConfigHex(HardwareLib.ConfigName.READER_CONFIG_INFO_L3,
    "09 43 41 53 30 30 30 30 30 30 30 30 30 30 30 31 30 30 30 30 30 30 30 30 30 30 30 31 00 01 00 00 00 20")

The checksum is never part of these payloads — the transport computes and appends the MDB CHK byte (8-bit sum) on every send automatically.

NEW — 7.10.0RS232 — configurable RX → TX rules

The machine talks over the CM30 serial port; the library answers from a rule table you define - up to 20 commands, added at runtime (code or dashboard JSON), persisted, hot-reloaded. "When rx this, tx this":

Rs232Lib.setRulesJson("""[
  {"name":"STATUS",       "rx":"FF FF FF FF FF", "tx":"01 00"},
  {"name":"VEND_REQUEST", "rx":"F1 05 ?? ?? 0D", "tx":"06", "priceHi":2,  "priceLo":3},
  {"name":"VEND_VARLEN",  "rx":"F2 *",           "tx":"06", "priceHi":-3, "priceLo":-2}
]""")
Rs232Lib.open(baud = 9600)
Rs232Lib.vendRequestListener = { price, frame -> /* charge, then Rs232Lib.sendHex(approvalHex) */ }

?? in an rx pattern matches ANY ONE byte - a vend request whose price bytes change still matches one rule - and a single trailing * matches ANY NUMBER of remaining bytes, for frames whose LENGTH varies ("A0 01 *" matches every frame starting A0 01). Two price formats, positions 0-based from the frame start or NEGATIVE from the frame end (-1 = last byte): binary priceHi/priceLo (price = hi×256+lo), or ASCII amountStart/amountEnd for card-reader protocols where the amount is digit text (31 35 30 30 30 30 = "150000" = 1500.00) - amountEnd is EXCLUSIVE, so -1 stops before a trailing CRC byte. Either way the price lands in vendRequestListener. Frames are cut from the stream by silence (frameGapMs, default 1000 ms - tune live with rs232Gap:MS); first matching rule wins; replies are written before logging.

Framed replies: buildXorFrame(header, dataHex) builds [header][2-byte length][data][XOR CRC]; sendXorFrame / sendXorAscii("A1 02", "SUCCESS") build and send - length and CRC computed for you (→ A1 02 00 07 53 55 43 43 45 53 53 E7); asciiHex("SUCCESS") converts text to hex.

Incoming CRC validation: setCrcCheck(true) (persisted, dashboard rs232Crc:on|off) - a received frame whose last byte is not the XOR of all preceding bytes is DISCARDED with no reply and no listeners, exactly as the card-reader protocol requires; the log shows CRC FAIL (expected XX) - discarded. Default off. Manual TX any time with sendHex(hex); exchangeListener gets every frame (rxHex, ruleName, txHex, price). Dashboard commands: rs232Open[:9600[,8,1,N]], rs232Close, rs232Send:HEX, rs232SendFrame:HEADER;DATAHEX, rs232SendAscii:HEADER;TEXT, rs232Simulate:HEX, rs232Crc:on|off, getRs232Rules, clearRs232Rules, and {"setRs232Rules":[...]} to push the whole table remotely.

The RS232 codebook schema (7.17.0 / mqtt-lib 2.2.0+): serial exchanges ship as coded RABBAH_LOG items, schema "RS232" - parseable exactly like MDB instead of raw text. Codes continue after the MDB CMD schema (110-136), so an RS232 code can never be confused with an MDB one: 137 RS232_RX_MATCHED [rule, rx, tx|-, price], 138 RS232_RX_UNMATCHED [rx], 139 RS232_CRC_DISCARDED [rx, expected], 140 RS232_TX [tx], 141 RS232_PORT_OPEN [params, ruleCount], 142 RS232_PORT_CLOSED, 143 RS232_RULES_LOADED [count]. Wire it with HardwareLib.addRs232EventListener { name, p -> RabbahLog.rs232(name, p) } - the demo bridge and attachRabbahMqtt() do this automatically. With a listener wired, the plain [rs232] ... twin stays LOCAL-only (each exchange crosses the wire exactly once); with none, plain lines ship as before. getCodebook now serves the RS232 schema, so dashboards decode it with zero changes.

Testing without the machine: Rs232Lib.simulateFrame(hex) feeds a fake received frame through the matcher exactly as if the machine sent it - matching, price extraction and both listeners all run; the reply is really written when the port is open, otherwise only logged. The RS232 Test bench APK (rs232-sample-v2.0.apk, source samples/Rs232SampleActivity.kt) puts the whole workflow on buttons: rule JSON editor (LOAD / GET / CLEAR), baud + OPEN / CLOSE PORT, SIMULATE RX, SEND HEX, live [rs232] log.

NEW — 7.5.0Pulse output — PulseLib

Pulse driving over the CM30's digital IO (android.hardware.digital.DigitalIO). A stretched pulse width is a rejected pulse, so the engine drives EVERY edge itself via digital_out_set_value on a dedicated PulseWorker thread at URGENT_AUDIO priority - active level for width ms, idle for (period - width) ms, exactly count times, with deadline-based sleep-then-spin waits. The vendor's own digital_out_pulse is NOT used for trains: tested on real hardware (7.9.3) it produced the wrong pulse count and ignored the direction - it remains available as vendorPulse(p1,p2,p3,p4) for experiments only.

// polarity, from the backend/dashboard boolean:
PulseLib.initPulse(true)    // HIGH-pulse mode: pin idles LOW now, pulses go HIGH
PulseLib.initPulse(false)   // LOW-pulse mode:  pin idles HIGH now, pulses go LOW

// send a train and get the REAL result (true = every pulse physically sent):
val ok = PulseLib.sendPulse(pulseWidthMs = 50, pulsePeriodMs = 100, count = 3)

sendPulse BLOCKS until the train finishes (about period x count) and returns true only when every pulse was written - call it from a coroutine, never the UI thread. initPulse drives the idle level immediately and may be called again whenever the backend changes the setting; sendPulse refuses to run before it. State: isInitialized / isHighPulse / pendingTrains. Ready feedback (7.9.x): setReadyFeedback(supported, expectedValue[, channel]) takes the dashboard flag directly (supported=false or a null value disables the gate); the value-only form setReadyFeedback(expectedValue, channel) arms a digital-in gate - before every train the input must equal the expected value or the pulse is refused; null disables the gate (machine without ready feedback), and isMachineReady() runs the check on demand. Dashboard commands: initPulse:true|false and sendPulse:50,100,3, setReadyFeedback:value[,channel]|off, checkMachineReady (width,period,count - remote trains run detached, results arrive as [pulse] sent ... log lines). vendorPulse(p1,p2,p3,p4) is a raw passthrough to the vendor's native digital_out_pulse for experiments. Without the CM30 runtime everything degrades to reported failures, never a crash.

08MQTT for your own app - RabbahMqtt & RabbahLog

RabbahMqtt is the one-stop generic surface - usable with ZERO MDB involvement. Every send is queued (never blocks, buffers offline, silent no-op when MQTT is off); every subscription re-establishes itself on reconnect. Topics are always <prefix>/<deviceId>/<suffix> - callers never build one.

Sending

// logs - ride the compact RABBAH_LOG envelope, render on the dashboard automatically:
RabbahMqtt.sendLog("payment gateway responded in 420ms")
RabbahMqtt.sendError("gateway timeout after 3 retries")     // severity=e, renders red

// JSON or plain text to any custom channel .../<deviceId>/<suffix>:
RabbahMqtt.sendJson("telemetry", JSONObject().put("battery", 87))
RabbahMqtt.sendText("status", "READY")

Receiving

// the command inbox - plain-text messages on .../commands (first-consume-wins chain):
val cmdSub = RabbahMqtt.onCommand { cmd ->
    when (cmd) {
        "rebootKiosk" -> { scheduleReboot(); true }   // true = consumed, chain stops
        else -> false                                 // false = let other listeners look
    }
}
RabbahMqtt.removeCommand(cmdSub)

// any custom channel, both formats:
val s1 = RabbahMqtt.subscribeJson("inbox")   { json -> ... }  // non-JSON arrives as {"raw":"..."}
val s2 = RabbahMqtt.subscribeText("control") { text -> ... }
RabbahMqtt.unsubscribe(s1)

Handlers run on the MQTT reader thread - return quickly, never block, hop to your own coroutine for real work. Return false from onCommand for anything you don't recognize: hardware-lib's own listener sits on the same chain, ping is answered (PONG) by mqtt-lib itself, and anything nobody consumes is reported back as unknown command.

RabbahLog - the compact envelope every log rides

Log lines are not free text on the wire. Each call becomes ONE compact JSON item on liveLog (single-letter keys, positional params); hardware-lib emits these automatically for every bus exchange, and sendLog/sendError use the same path:

RabbahLog.init("vending-app", "2.13.5")   // once - stamps "a" and "v" on every item

// on the wire:
RABBAH_LOG:{"t":"1787743651002","s":"MDB","m":"13","a":"vending-app","v":"2.13.5",
            "k":"i","i":"7c1f2a9b","d":1,"p":["13 00 01 5E 00 0C 78","ACK","350","12"]}

t = epoch ms; s+m = codebook entry (schema + message code); a/v = emitter; k = severity i/e/d; i = session id correlating every log of one vend; d = 1 buffered / 2 instant; p = positional params (for MDB events p[0] is always the rx frame, p[1] our reply). The sentence itself is never on the wire: the dashboard fetches this build's dictionary once (getCodebook -> CODEBOOK_JSON:{...}) and renders through the same RabbahLog.format() substitution the on-device screen uses, so the two can never show different wording. RabbahLog.makeLogJson(...) builds the envelope without sending.

The block a fleet app should actually ship (only 7 values differ from defaults — passthrough and auto-attach are already right):

MqttLib.init(MqttConfig(
    topicPrefix        = "devices",
    deviceId           = deviceCode,               // e.g. "D-5007"
    brokerHost         = BuildConfig.MQTT_HOST,    // uat-api.rabbah.sa - from local.properties
    brokerPort         = 1883,
    username           = BuildConfig.MQTT_USERNAME,
    password           = BuildConfig.MQTT_PASSWORD,
    logTopicSuffix     = "logs",
    commandTopicSuffix = "cmd",
    statusTopicSuffix  = "status"
))
MqttLib.start()
// That's the ENTIRE integration on 2.3.0: on first connect mqtt-lib auto-attaches
// hardware-lib (logs + all remote commands). No bridge code, no attach call.

With statusTopicSuffix set, a retained online is published on every connect, the broker publishes a retained offline via Last Will if the device drops, and a graceful stop() publishes offline itself. The suffix fields exist for the Rabbah backend contract (devices/{deviceCode}/logs|cmd|status); the defaults keep the existing dashboard wire format untouched, and the dashboard follows a re-pointed device via ?logTopic=logs&cmdTopic=cmd.

Attaching hardware-lib — three ways, first one wins (all idempotent, a second attach wires nothing twice): (1) automatic — mqtt-lib 2.3.0 does it on first connect (the default path); (2) from the dashboard — the Attach HW toolbar button (or typing attachHardware in the passthrough bar) wires it remotely on demand, and replies with success or the reason it can't; (3) in code — HardwareLib.attachRabbahMqtt(), the pre-2.3.0 way, still works. Check what a device is running any time with the Version button / version command.

Point the dashboard at the same broker over WebSocket: Hardware Dashboard.exe (dashboard-app, F2 sets broker / user / password) (values persist in localStorage; a browser cannot speak plain TCP 1883).

The low level, still public

MqttLib.enqueue("[app] plain legacy line")      // raw string to liveLog - still works
MqttLib.enqueue("telemetry", "json-or-text")    // raw string to a custom suffix
MqttLib.addCommandListener { cmd -> ... }        // what onCommand wraps

Diagnostics

MqttLib.isConnected       // broker link up right now? (sends work either way)
MqttLib.pendingMessages   // waiting in the queue - 0 means fully drained
MqttLib.droppedMessages   // lost to queue overflow - rising = offline too long

rabbahlog-sample-v1.1.apk (in the deliverable folder) exercises all of this: on-screen broker settings, log/telemetry/burst buttons, a live queued/sent/dropped line, and an inbox subscription to hit with mosquitto_pub.
