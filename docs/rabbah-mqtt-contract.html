Rabbah Device MQTT Contract

The topic scheme between field devices and the Rabbah backend (apps/api, MQTT client id legacy-backend). Devices publish logs, acks, progress, and presence; the backend publishes remote commands. Everything is keyed by the human-readable {deviceCode}.

01 · whereBroker

# backend .env
MQTT_URL=mqtt://mosquitto:1883       # in-cluster hostname; plain TCP
MQTT_USERNAME=rabbah
MQTT_PASSWORD=********              # real value lives in the backend .env only
MQTT_CLIENT_ID=legacy-backend

The device side connects to the same mosquitto with the same credentials via MqttConfig(brokerHost, brokerPort, username, password); the dashboard reaches it over the WebSocket listener (log-viewer.html?broker=ws://HOST:9001&user=…&pass=…).

02 · device → backendInbound (backend subscribes)

The backend subscribes through $share/rabbah-api/<topic> — the $share/rabbah-api/ prefix is only a shared-subscription group name, so when several apps/api replicas are running, the broker delivers each message to exactly ONE of them instead of all. Devices publish to the plain topic — the prefix never appears in what a device sends.

TopicPurpose
INdevices/{deviceCode}/logsSingle device log
INdevices/{deviceCode}/logs/bulkBatched device logs
INdevices/{deviceCode}/cmd/ackDevice acknowledges a remote command
INdevices/{deviceCode}/cmd/progressRemote command progress updates
IN · retaineddevices/{deviceCode}/statusPresence — online published as the birth message on connect, offline written by the broker via LWT when the device drops. Retained, so a late subscriber immediately sees the last known state.

03 · backend → deviceOutbound (backend publishes)

TopicPurpose
OUTdevices/{deviceCode}/cmdSend a remote command to a device
OUTdongles/{deviceCode}/cmdSend a dongle command — payload is {} for now, per RHT-924

The command round-trip pairs with the inbound side: the backend publishes to …/cmd, the device answers on …/cmd/ack and streams long-running work on …/cmd/progress.

04 · identityDevice codes

{deviceCode} is the human-readable code like D-0123 — not the raw integer database id. Every topic in this contract uses it, so a device must know its own code before it can publish or subscribe anywhere.

05 · the device sideMapping to mqtt-lib / RabbahMqtt

The device libraries build every topic as <topicPrefix>/<deviceId>/<suffix>. Pointing them at this contract is one config line: 

MqttLib.init(MqttConfig(
    topicPrefix        = "devices",
    deviceId           = "D-0123",          // the deviceCode, not ANDROID_ID
    brokerHost         = "YOUR-SERVER", brokerPort = 1883,
    username           = "rabbah", password = "...",
    logTopicSuffix     = "logs",            // automatic log stream -> devices/D-0123/logs
    commandTopicSuffix = "cmd",             // command listener chain <- devices/D-0123/cmd
    statusTopicSuffix  = "status"           // retained online/offline presence
))

// the remaining channels line up as plain suffixes:
RabbahMqtt.sendJson("logs/bulk", batch)            // -> devices/D-0123/logs/bulk
RabbahMqtt.sendJson("cmd/ack", ack)                // -> devices/D-0123/cmd/ack
RabbahMqtt.sendJson("cmd/progress", progress)      // -> devices/D-0123/cmd/progress
// commands from the backend arrive on the normal listener chain:
val sub = RabbahMqtt.onCommand { cmd -> /* handle, return true to consume */ false }

Both former gaps are built (mqtt-lib 1.3.0):

1. Channel suffixes are configurable. logTopicSuffix / commandTopicSuffix in MqttConfig point the AUTOMATIC log stream and command listener at …/logs and …/cmd. The defaults stay liveLog / commands, so every existing device and the dashboard keep working unchanged; the dashboard follows a re-pointed device via log-viewer.html?logTopic=logs&cmdTopic=cmd.

2. Presence is implemented. Setting statusTopicSuffix = "status" publishes a RETAINED online birth message on every connect, registers an MQTT Last Will so the broker publishes a retained offline when the device drops, and a graceful MqttLib.stop() publishes the retained offline itself (a clean disconnect never fires the Will). Leaving it null (the default) produces no presence traffic at all.

06 · worked examplesOne message per topic

Every payload below is real: the log items are exactly what mqtt-lib's RabbahLog envelope produces on the device today (t/s/m/a/v/k/i/d/p, decoded via the codebook), and the command round-trip shows the shape a device answers with.

IN devices/D-0123/logs - single log

// a vend request as the device ships it (schema MDB, code 13 = MDB_VEND_REQUEST):
{"t":"1787743651002","s":"MDB","m":"13","a":"vending-app","v":"2.13.6",
 "k":"i","i":"7c1f2a9b","d":1,"p":["13 00 01 5E 00 0C 78","ACK","350","12"]}

// a free-text app log (schema INFO, code 0 = INFO_RAW):
{"t":"1787743652390","s":"INFO","m":"0","a":"vending-app","v":"2.13.6",
 "k":"i","d":1,"p":["payment gateway responded in 420ms"]}

IN devices/D-0123/logs/bulk - batched logs

// a JSON array of the same items, oldest first:
[
  {"t":"1787743650120","s":"MDB","m":"8", "a":"vending-app","v":"2.13.6","k":"i","i":"7c1f2a9b","d":1,"p":["12 12","03 FF FF 00 00 00 01 00 00 00"]},
  {"t":"1787743651002","s":"MDB","m":"13","a":"vending-app","v":"2.13.6","k":"i","i":"7c1f2a9b","d":1,"p":["13 00 01 5E 00 0C 78","ACK","350","12"]}
]

// device side:  RabbahMqtt.sendJson("logs/bulk", batchArrayAsString)

OUT devices/D-0123/cmd - backend sends a command

// backend publishes (example - the device treats the payload as one command string
// on its listener chain; JSON config commands work too, exactly like the dashboard's):
vendApprove
{ "setConfig": { "SESSION_BEGIN_L2": "03 FF FF" } }

IN devices/D-0123/cmd/ack - device acknowledges

// device side:  RabbahMqtt.sendJson("cmd/ack", ack)
{"cmd":"vendApprove","ok":true,"t":"1787743651900","detail":"VEND APPROVED armed for next POLL"}
{"cmd":"setConfig","ok":false,"t":"1787743652100","detail":"Wrong length for VEND_APPROVED: got 2 byte(s), need 3"}

IN devices/D-0123/cmd/progress - long-running command updates

// device side:  RabbahMqtt.sendJson("cmd/progress", progress)
{"cmd":"firmwareUpdate","pct":40,"t":"1787743660000","stage":"downloading"}
{"cmd":"firmwareUpdate","pct":100,"t":"1787743699000","stage":"done"}

IN · retained devices/D-0123/status - presence

// published automatically by mqtt-lib 1.3.0 when statusTopicSuffix = "status":
online     // retained birth message, on every connect
offline    // retained - from the broker's Last Will on a drop, or from a graceful stop()

OUT dongles/D-0123/cmd - dongle command

{}         // payload is empty JSON for now, per RHT-924

Testing from a PC

# watch everything one device says:
mosquitto_sub -h YOUR-SERVER -u rabbah -P '...' -t 'devices/D-0123/#' -v

# send it a command:
mosquitto_pub -h YOUR-SERVER -u rabbah -P '...' -t 'devices/D-0123/cmd' -m 'ping'
# the device answers PONG on its log channel; presence shows instantly because status is retained

Note the ack/progress JSON shapes above are the proposed device-side convention (the contract fixes the topics, not the payloads) - if the backend already expects specific field names on cmd/ack / cmd/progress, those win and the device should mirror them.
