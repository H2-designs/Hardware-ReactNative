The two-library architecture

Everything proven in the MDB Slave app now lives in two Android libraries — mqtt-lib and hardware-lib — consumed as AARs. This is the as-built reference: module boundaries, every data flow, the payment-gateway VendListener, and the exact public API. The demo app is a ~140-line thin integration of exactly what any Android developer would write.

01 — the boundariesModule & dependency diagram

Two libraries, one demo app. The dependency arrow points one way only: hardware-lib uses mqtt-lib's queue to ship its data to the dashboard; mqtt-lib has zero knowledge of MDB. The developer's own app depends on both and can use mqtt-lib independently (for its own logs) even where MDB isn't involved.

Why hardware-lib calls the queue directly (instead of the app relaying): MDB data reaches the dashboard without the app developer writing any glue — install both AARs, call init(), done. The engine still exposes local listeners so the app can mirror the same data in its own UI, but the MQTT path works even if the app ignores them.

NEW — the 7.x splithardware-lib: the MDB engine, MQTT-free

mdb-lib is now hardware-lib-7.2.0 — renamed, and with the entire MQTT layer removed from inside it. The engine is pure hardware/protocol: everything it produces exits through listeners, everything it accepts enters through plain functions. The Kotlin package stays com.rabbah.mdb and a deprecated typealias MdbLib = HardwareLib keeps existing code compiling.

The MQTT wiring that used to be automatic now lives in a ~30-line app-side bridge (MdbMqttBridge.kt, shipped in samples/) that reproduces the old wire format byte-identically — the dashboard needs zero changes:

// the whole bridge - attach BEFORE HardwareLib.init():
MqttLib.addCommandListener { HardwareLib.handleCommand(it) }        // commands in
HardwareLib.controlListener = { tag, payload ->                     // control plane out
    if (tag == "LOG") MqttLib.enqueue(payload) else MqttLib.enqueue("$tag:$payload")
}
HardwareLib.exchangeListener = { e ->                               // exchanges out
    if (e.publishRemote) {
        RabbahLog.sessionId = e.sessionId
        RabbahLog.log(MdbLogEvent.valueOf(e.logEventName), e.params)
    }
}

New listener surface: stateListener (plain state name, edge-triggered on every transition), exchangeListener (one structured MdbExchangeEvent per exchange), controlListener (tag + JSON for SETTINGS_JSON / CONFIG_JSON / VMC_STATUS / LOG), plus the existing vendListener / logListener / statusListener. New input: HardwareLib.handleCommand(text): Boolean — feed it whatever any transport receives; it consumes what it recognizes.

The CMD code schema. Every exchange carries one stable integer code (MdbCmd, append-only). Edit a reply by number with setReplyHex(code, hex) / read it with getReplyHex(code); the last frame the VMC sent per code is saved — lastReceivedHex(code) / lastReceivedJson():

02 — one door outOutbound queue flow

Everything that leaves the device goes through one bounded queue owned by mqtt-lib. Producers never touch the socket — they just enqueue() and return immediately. One publisher thread is the only consumer, so socket writes are serialized by construction: no races, no thread-per-message, no NetworkOnMainThreadException ever.

03 — one door inInbound command flow

Incoming MQTT messages are dispatched to registered listeners in order. hardware-lib registers its listener during init() and consumes every command it recognizes; the app developer registers their own for their custom commands. A listener returns true ("consumed") to stop the chain. ping is answered (PONG) by mqtt-lib itself before the chain; anything nobody consumes is reported back as unknown. Routing is recognition, not addressing — mqtt-lib never knows what MDB is.

04 — configs as JSON, owned by the libraryConfig flow

All config behavior — parsing, validation, persistence, live application, acknowledgment — lives inside MdbConfigStore. The dashboard sends JSON; the store does everything else. Nobody outside the library ever touches SharedPreferences or validates hex. 

// bulk update — any subset of names

06 — the money pathVendListener: one paid vend, end to end

The typed hook a payment app implements. The core idea: the money follows the product, not the button press — authorize on request, capture only after the VMC confirms the item physically dispensed, refund if it didn't. All callbacks run on the MDB worker thread: return immediately and do gateway work on your own thread; the engine keeps ACKing the VMC's polls while it waits (the spec's delayed-response pattern), so a gateway round trip of a few seconds costs nothing on the bus. 

// once at setup (persisted, so genuinely once):
HardwareLib.setCancelMode(HardwareLib.CancelResponse.VEND_DENIED)

HardwareLib.vendListener = object : HardwareLib.VendListener {
    override fun onVendRequest(amount: Double, minorUnits: Int, itemNumber: Int) {
        // minorUnits = 350 (EXACT integer halalas - for the gateway & money math)
        // amount     = 3.5 (decimal, for display). MDB worker thread - pay async:
        scope.launch {
            if (gateway.authorize(minorUnits)) HardwareLib.approveVend()
            else HardwareLib.cancelVend()          // simple call, uses the standing mode set above
        }
    }
    override fun onVendSuccess(itemNumber: Int) { scope.launch { gateway.capture() } }
    override fun onVendFailure()                { scope.launch { gateway.refund() } }
    override fun onSessionEnded()               { /* per-session cleanup */ }
}

Rules: never block inside a callback (a stalled bus loop makes the VMC time out and RESET the reader); exceptions you throw are caught and logged, never fatal; price/itemNumber are the raw 16-bit MDB values (-1 if the VMC omitted the item bytes) — scale price per your READER CONFIG DATA scale factor. Cancelled sessions skip success/failure and go straight to onSessionEnded(), which is why refund logic lives in onVendFailure and only cleanup lives in the session-end hook.

07 — the contractPublic API, as shipped

mqtt-lib (2.0.0)

class MqttConfig(
    val topicPrefix: String,              // e.g. "cm30-mdb/hamdan-rabbah"
    val deviceId: String,                 // shown on-screen; separates machines
    val brokerHost: String = "the Rabbah mosquitto",
    val brokerPort: Int = 1883,
    val keepAliveSec: Int = 30,
    val queueCapacity: Int = 1000
)

object MqttLib {
    fun init(config: MqttConfig)
    fun start() / stop()
    fun enqueue(payload: String)                          // -> liveLog; THE one way out
    fun enqueue(topicSuffix: String, payload: String)     // custom channel
    fun addCommandListener(listener: (String) -> Boolean) // true = consumed
    fun removeCommandListener(listener: (String) -> Boolean)
    val isConnected: Boolean
    val droppedMessages: Long                             // queue-overflow counter
}

hardware-lib (6.4.1)

object HardwareLib {
    fun init(context: Context)   // MQTT optional: without it HardwareLib runs fully offline
    fun start() / stop()         // open/close the MDB port + worker loop

    // vend actions
    fun beginSession()                                 // the "card tap" (manual mode)
    fun approveVend(): Boolean                         // false if no VEND REQUEST pending
    fun cancelVend(): Boolean                          // simple: sends the standing mode
    fun cancelVend(response: CancelResponse): Boolean  // one-time override

    // state, readable on demand
    val currentState: String        // INACTIVE_STATE | DISABLED_STATE | ENABLED_STATE | VEND_STATE
    val isSessionActive: Boolean

    // settings - each also a dashboard command; persisted; SETTINGS_JSON auto-published
    fun setCancelMode(mode: CancelResponse)            // set ONCE, then cancelVend() is enough
    fun setAutoSession(enabled: Boolean); val isAutoSession: Boolean
    fun setMdbLevel(level: Int)                        // 1 | 2 | 3
    fun setMqttLogging(enabled: Boolean); val isMqttLoggingEnabled: Boolean
    fun setPollVisibility(show: Boolean) / setUnhandledVisibility(show: Boolean)
    fun currentSettingsJson(): String

    // hex payloads - from Android code, dashboard auto-synced on every change
    object ConfigName { SESSION_BEGIN, READER_CONFIG_DATA, ... }   // name constants
    fun getConfigHex(name): String / setConfigHex(name, hex): String? / resetConfig(name)
    fun configNames(): List<String> / configSnapshotJson(): String

    // price conversion (also applied automatically before onVendRequest)
    fun priceToAmount(raw: Int): Double / priceToMinorUnits(raw: Int): Int

    enum class CancelResponse { SESSION_CANCEL_REQUEST, VEND_DENIED }

    interface VendListener {
        fun onVendRequest(amount: Double, minorUnits: Int, itemNumber: Int)
        fun onVendSuccess(itemNumber: Int)
        fun onVendFailure()
        fun onSessionEnded()
    }
    var vendListener: VendListener?
    var logListener: ((line: String, showOnScreen: Boolean) -> Unit)?
    var statusListener: ((stateJson: String) -> Unit)?   // instant on state change + 3s heartbeat
}

object MdbConfigStore {
    fun applyJson(json: String): ApplyResult   // parse + validate + persist + acks, inside
    fun snapshotJson(): String
    fun get(name) / set(name, hex): String? / resetToDefault(name) / names()
}
