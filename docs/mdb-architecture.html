How the MDB Slave app works

An Android app on the CM30 terminal impersonates an MDB Cashless Device #1 on a real vending machine bus, while a browser page anywhere on the internet watches every byte and drives it remotely. This document states exactly what each piece does, which bytes trigger which responses, and where every decision is made in the code.

01 — the shape of itSystem overview

Three parties, two links:

  • VMC ↔ Android app — the real MDB bus. The vending machine controller (VMC) is the master; it polls constantly and our app answers as slave address 0x10 (Cashless Device #1, command range 0x10–0x17). Byte I/O goes through the CM30 vendor library.
  • Android app ↔ PC browser — MQTT over the public broker broker.hivemq.com:1883 (the PC side connects via WebSocket on 8884). Both sides only make outbound connections, so this works across the internet with no port forwarding, VPN, or fixed IP. It is not a private channel — anyone who knows the topic strings can read or write them.

Inside the app, the core rule is: the MDB protocol engine and the MQTT client never reference each other. MdbProtocolEngine has no network imports; MqttBridge has no MDB knowledge. The single place they meet is MdbSlaveActivity, which implements the engine's Listener interface on one side and owns the MQTT callbacks on the other.

02 — who owns whatComponents

MdbProtocolEngine.kt

The full slave state machine: 4 states, per-level setup handshakes, the vend cycle, global RESET. Runs one worker thread. Reports outward only via Listener.onExchange() / onVmcStatus().

MdbSlaveActivity.kt

The only coordinator. Implements the engine's Listener, owns appendLine() (screen + LogServer + MQTT), parses every remote command string into an engine/config method call. Contains zero protocol logic.

MdbSlaveWrapper.kt (×2 flavors)

device: real CM30 hardware I/O. simulator: scripted fake VMC for emulators. Identical API. Both compute the MDB checksum (8-bit sum, appended as last byte) and fetch every payload fresh from MdbConfig on each send.

MqttBridge.kt

Hand-rolled MQTT 3.1.1 client (CONNECT / PUBLISH QoS 0 / SUBSCRIBE / PINGREQ — no library). Auto-reconnects every 3 s on drop. All socket writes happen on background threads so UI-thread callers can never hit NetworkOnMainThreadException.

MdbConfig.kt

The wire payloads themselves — every response's raw bytes, persisted in SharedPreferences, editable live from the PC page via setConfig:NAME:hex. Length is locked per name; only values change.

AppSettings.kt

Persisted behavior flags: session-begin mode (auto/manual), VMC-cancel response mode, MDB level (1/2/3), POLL and unhandled-traffic visibility. Loaded once at startup into the engine.

LogServer.kt

Local WebSocket server for the USB/adb-forward path — receives the same log lines as MQTT, for bench use with a cable instead of the internet.

log-viewer.html

The whole PC control surface in one static file: live log, multi-device picker, all toggles, and the per-byte Config editor with level-aware rows.

03 — the wire between app and browserRemote protocol (MQTT)

Each physical device derives a 6-character ID from its ANDROID_ID (shown on its screen, e.g. 85E5F7) and scopes its two topics with it, so many machines can share the broker without colliding:

  • cm30-mdb/hamdan-rabbah/<deviceId>/liveLog — device → PC. Every log line, plus tagged machine-readable messages (below).
  • cm30-mdb/hamdan-rabbah/<deviceId>/commands — PC → device. Plain text commands.

The PC page subscribes to the wildcard …/+/liveLog, so every online device self-announces into its device dropdown; commands are published only to the selected device's topic.

04 — who calls whomData flow

Bus traffic flows left to right; remote commands flow right to left along the dashed arrows. The engine's only outward surface is the two Listener callbacks — it cannot name MQTT, LogServer, or the screen.

Performance note that shaped this design: appendLine() redraws the entire on-screen TextView from a growing StringBuilder on every call. POLL arrives many times per second, so routing suppressible traffic (idle ACKs, unhandled commands, other peripherals' bytes) to the screen froze the app on real hardware. The engine therefore passes showOnScreen=false for those lines — they still reach MQTT/LogServer for debugging, but never the device display.

05 — the actual brainInside the protocol engine

Two threads run while the port is open. The bus thread (MdbSlaveLoop, urgent priority) does nothing but read one command → processCommand() → send the response — the VMC allows only a few milliseconds between its command and our answer, and setup commands arrive back-to-back, so after every command the loop spins hot for a 15 ms burst window instead of sleeping (Android's 1 ms sleep routinely oversleeps to 10–20 ms, which was enough for real machines to discard our READER CONFIG responses and loop the handshake). Everything else — hex log formatting, listener callbacks, vend callbacks, status JSON, MQTT enqueueing, the 3-second heartbeat — is pushed onto a bounded queue and executed in order by the offload thread (MdbOffload), so no bookkeeping can ever sit inside the reply window. Every received command passes three gates, in this exact order:

  1. Address filter. First byte outside 0x10–0x17 means the VMC is talking to some other peripheral (coin changer, bill validator…). Never answered; optionally logged as "ignored — other peripheral" when unhandled-visibility is on.
  2. Global RESET. 0x10 from any state: reply ACK, jump to INACTIVE_STATE, reset the JUST RESET counter to 0 so the next POLLs get a genuine fresh announcement (up to 5 of them). Handled once, before the per-state dispatch, so no state can ever forget it. The re-announcements are only a nudge for a VMC that ignored the first one: the moment any setup command is answered, JUST RESET is marked consumed and never repeats — re-announcing it mid-handshake makes the VMC restart setup in a loop (observed on real hardware).
  3. Per-state dispatch. when(mdbState), and inside INACTIVE_STATE a second dispatch when(mdbLevel) into one of three dedicated setup handlers — processInactiveStateLevel1/2/3(). Each is a self-contained switch with no level checks inside it.

Every branch ends by setting a sent label, which drives exactly one of three logging outcomes: a normal line, a suppressible ACK (shown only if POLL visibility is on), or — when no branch matched — an UNHANDLED line (shown only if unhandled visibility is on). "We answered but hid it" and "we didn't answer at all" are therefore always distinguishable in the remote log.

06 — byte by byteThe setup handshake, per level

This is the exact conversation from power-on to "ready to sell", per configured level. RX is what the VMC sends; TX is our reply. Trailing checksums omitted — the wrapper appends the 8-bit-sum CHK byte to every multi-byte reply; bare ACK is a single byte with no checksum, per spec.

The feature-bits bytes are the truth, not a setting. Per the MDB/ICP spec (§7.4.4), the 32 optional-feature bits are sent MSB-first: Z31 carries bits 31–24 and Z34 — the last byte — carries bits 7–0, which are the only ones currently defined (b0 FTL, b1 32-bit money, b2 multi-currency, b3 negative vend, b4 data entry, b5 Always Idle, b6 remote vend, b7 basket). The engine's alwaysIdleDeclared() reads bit 5 of Z34 directly out of the READER_CONFIG_INFO_L3 hex in MdbConfig — to enable Always Idle you edit that byte (e.g. set it to 20) in the Config panel. There is deliberately no separate toggle that could disagree with what's declared on the wire. All four bytes default to 00: zero optional features claimed.

07 — the money pathOne vend, start to finish

Everything below happens in ENABLED / VEND. The slave never initiates — every TX below is the answer to a POLL or a direct command. Pending flags (sessionBeginPending, vendApprovePending, sessionCancelPending, endSessionPending) are armed by events and consumed by the next POLL.

#DirBytesWhat happens
1RX 12POLLsessionBeginPending is armed (auto-mode, or the Begin Session button) → TX BEGIN SESSION (03 + funds — 3 bytes at L1, 10 at L2/3) · → VEND
2RX 13 00 PH PLVEND REQUESTACK · price bytes stored · vendRequestReceived = true. Customer picked an item; VMC asks permission.
3—operatorvendApprove arrives (button / remote). Accepted only because a request is pending — otherwise rejected outright, never queued, so it can't auto-approve the next customer's item.
4RX 12POLLTX VEND APPROVED (05 + the stored price). Flags cleared so a stale approval can't fire twice.
5RX 13 02VEND SUCCESSACK — product was dispensed.
6RX 13 04SESSION COMPLETEACK · endSessionPending = true.
7RX 12POLLTX END SESSION (07) · → ENABLED · auto-mode re-arms for the next cycle.

The exits that aren't a sale

  • Cancel (either side): the VMC's VEND CANCEL (13 01) or our cancelVend arms sessionCancelPending; the next POLL gets exactly the configured response — SESSION CANCEL REQUEST (04) or VEND DENIED (06), no substitution — and the vend cycle's price/flags are wiped.
  • VEND FAILURE (13 03): ACK immediately (refund handshake); the idle-POLL default ACK covers the "refund done" phase. No real refund logic exists yet — only the wire handshake.
  • Mode switch mid-session: flipping auto↔manual while a session is live immediately cancels it, so the new mode takes effect on the next session instead of being silently ignored; flipping while merely ENABLED arms/disarms sessionBeginPending on the spot.
  • Always Idle (L3, bit declared): step 1 is skipped entirely — a VEND REQUEST arriving straight in ENABLED is ACKed and enters VEND directly.
  • REVALUE (Level 2/3, in-session): REVALUE LIMIT REQUEST (15 01) is answered with REVALUE LIMIT AMOUNT straight from the REVALUE_LIMIT config; a REVALUE REQUEST (15 00, the VMC wanting to credit funds onto the media) is always answered REVALUE DENIED (0E, config-editable) — this device is a gateway-backed payment reader, not a stored-value card. At Level 1 the command doesn't exist and stays unhandled.

08 — one setting, real divergenceWhat the level actually changes

The level isn't cosmetic — it changes which commands exist at all. It's selected on the PC page, persisted on the device, and implemented as three separate setup switches (processInactiveStateLevel1/2/3()) dispatched by one when(mdbLevel); everything after DISABLED_STATE is shared because it genuinely doesn't differ.

Config rows shown on the PC pageThe Config panel hides every row that doesn't exist at the selected level — e.g. at Level 1 you see no Peripheral ID, no Revalue Limit, and only the 3-byte Begin Session.

Retry tolerance in DISABLED_STATE, learned from hardware: real VMCs keep resending setup commands even after they were answered, and won't send READER ENABLE until every one gets a reply. Machines also don't agree on the ORDER: one real machine sends SETUP CONFIG → EXPANSION REQUEST ID → then SETUP MAX/MIN, so a SETUP command can legitimately arrive after we already moved to DISABLED. So DISABLED_STATE re-answers every setup command without changing state — SETUP CONFIG DATA (11 00), SETUP MAX/MIN (11 01), EXPANSION REQUEST ID (17 00), EXPANSION ENABLE OPTIONS (17 04) — and only genuinely unexpected traffic stays UNHANDLED.
